| 10 个风格模板，`StylePreset` 有 `key`/`name`/`caption`/`duration`/`vocal_language`/`verified`/`note`/`bpm` | `styles.py` | 下拉框直接由 `list_presets()` 生成；`verified` 可做「实测」角标 |

| `songs/` 已在 `.gitignore` 里 | `.gitignore` | 历史列表读的是本地产物，不随仓库分发 |

## 1. 产品目标

### 这次要解决的问题

现在这个项目**只有开发者能过第一关**。想给妈妈做歌的人卡在三处：

1. **进不去**：得先知道什么叫"命令行"，要 `cd` 到目录、要敲 `python -m song_for_someone make --style folk --lyrics-file lyrics.txt -o 给妈妈的歌.mp3`。少一个字符就是一堆英文报错。
2. **看不见反馈**：歌词体检（`lyrics.analyze()`）是本项目最实在的功能之一，但它只在终端里出现。用户在界面上是"盲写"——写完、等 20 秒、出来发现副歌缺了、某一行太长了，只能重来。
3. **看不出活着**：终端只有 `[5s] 生成中 .` 这种输出。普通人第一反应是"是不是卡死了"，然后关掉窗口，把正在跑的任务一起关掉。

另外，"完整项目结构"这一条指的是观感：现在打开仓库只看到一个包 + 三个脚本，**不像一个可以递给别人的成品，像一个演示**。缺少启动入口、缺少界面相关目录、缺少对应的文档索引。

### 做成什么样算成功（可验收）

| 目标 | 验收判据 |
|---|---|
| **G1 零命令行** | 用户从下载到听到歌，**全程不需要打开终端、不需要输入任何命令**。起点是双击一个文件。 |
| **G2 看得见的体检** | `lyrics.analyze()` 产出的 `error`/`warn`/`hint` 三级问题，**100% 能在界面上看到**，且在用户打字过程中就出现，不用等提交。 |
| **G3 诚实的等待** | 生成过程有持续的视觉反馈；界面任何位置**都不出现**把估算当真实进度的表述（详见 §4.3）。 |
| **G4 对着普通人说话** | 界面零裸术语：不出现 `caption` / `inference_steps` / `seed` / `guidance_scale` / `task_type` 等英文词；零英文 traceback。环境坏了给的是「双击哪个文件」级别的指引。 |
| **G5 不破坏现状** | 57 个测试继续全绿；`pyproject.toml` 的 `dependencies` 仍为 `[]`；6 个 CLI 子命令的**行为与输出不变**（Web 是新增，不是替换）。 |

## 2. 用户故事

覆盖「完全不懂命令行的普通人」从拿到项目到听到成品的完整旅程。

**US-1｜第一次打开（不会命令行）**
> 作为 一个想给妈妈做生日歌的人，我完全不懂命令行，
> 我希望 下载下来以后双击一个文件就能打开界面，
> 这样 我不用搞懂 Python 环境、不用敲命令，也不会在第一步就放弃。

验收：双击启动文件后 ≤ 15 秒，浏览器自动打开界面（或提示已打开的地址）。

**US-2｜不知道怎么选风格**
> 作为 一个不知道"民谣"和"温暖流行"有什么区别的人，
> 我希望 风格选项用中文名 + 一句大白话说明，
> 这样 我能按"我要送给谁"来选，而不是按音乐术语。

验收：下拉里每一项都是中文名（如「生日祝福 · 轻快」）+ 一句说明；选中后自动带出建议时长。

**US-3｜一边写一边被提醒（本项目的核心增值）**
> 作为 一个第一次写歌词的人，
> 我希望 我打字的时候界面就告诉我"这句太长了""你没有副歌""这个标签少了一对方括号"，
> 这样 我不用等 20 秒出歌之后才发现白写了一遍。

验收：输入停止后 ≤ 500ms 出现体检结果；`error`/`warn`/`hint` 三级视觉上可区分；每条提示用中文说清"哪里不对 + 怎么办"。

**US-4｜等待时不慌**
> 作为 一个已经点了「开始出歌」的人，
> 我希望 界面告诉我它现在在干什么、大概还要多久，并且明说这个时间是估的，
> 这样 我不会以为程序死了然后把窗口关掉，把正在跑的任务一起弄没。

验收：生成期间至少每 2 秒有一次可见的视觉变化；显示的剩余时间旁必有「估算」标注。

**US-5｜听到、拿到**
> 作为 一个刚出完歌的人，
> 我希望 直接在页面上试听，然后一键下载到电脑，
> 这样 我能马上把歌发给对方，不用去翻 `songs` 文件夹、不用搞懂 `.mp3` 在哪个盘。

验收：`<audio>` 可播放；下载按钮可用；同时显示时长、速度、调式（来自 `TaskResult.bpm` / `key_scale` / `duration` / `describe()`）。

**US-6｜环境没配好（最高频的失败）**
> 作为 一个环境还没弄好的人（ACE-Step 服务没启动 / 显卡显存不够 / 模型没下完），
> 我希望 界面直接告诉我"哪个程序没开、双击哪个文件去开"，
> 这样 我不会对着 `ServiceUnreachable: 连不上 http://127.0.0.1:8001` 发呆。

验收：服务不可达时，界面显示中文操作步骤（含 `start_api_server.bat`）+ 「我再试一次」按钮，**不出现 traceback**。

**US-7｜想改一版再出一版**
> 作为 一个听完觉得不满意的人，
> 我希望 我的歌词和选择都还在，我改两个字就能再出一版，
> 这样 我不用从头填一遍表单。

验收：生成完成后表单内容不丢；「改改歌词再出」回到表单且内容保留。

**US-8｜出过好几首之后**
> 作为 一个之前出过几首歌的人，
> 我希望 看到我之前出过的歌，能再播放、能下载、能照原样再出一版，
> 这样 我不用记得当时的风格和时长是怎么选的。

验收（P1）：列出 `songs/` 下的音频 + 同名 `.json` 元数据，支持播放 / 下载 / 参数回填。

## 4. Web UI 设计稿

### §4.1 设计原则

1. **界面不出现裸术语**。所有英文参数名必须映射为中文人话，或收进默认折叠的「更多设置」里。完整对照表见 §4.6。
2. **一个页面走完全程**。四个状态（填写 → 生成中 → 完成 → 出错）在同一个页面内切换，不跳转、不刷新、不丢输入。
3. **失败必须可行动**。每条错误信息都要能回答"我现在该干什么"。
4. **不假装聪明**。不确定的事（尤其"还要多久"）必须标明是估算。

### §4.4 屏幕 3：生成中 —— 诚实的进度条（本次难点）

#### 先说清 API 到底能给我们什么

```text
AceStepClient.wait(task_id, timeout, interval, on_progress)
    on_progress(elapsed: float, status: int)
    status ∈ {0 = 生成中, 1 = 成功, 2 = 失败}
```

**结论：上游只给三态轮询，没有真实百分比。** 而且客户端默认 `interval=5.0` 秒，也就是说服务端"事件"最快 5 秒才来一次。任何界面上的连续动画，**都只能是前端自己估的**。

用户明确要"一个进度条"。所以我们不能只给一个转圈——那会被认为"没做进度条"。但也绝不能把它伪装成真实进度。

#### 方案：**分段文案 + 已耗时分段估算条**（拒绝真实百分比伪装）

两层信息一起给：

**第一层 —— 阶段文案。** 按「已耗时 / 预估值」的比例切阶段，让用户知道"现在在干什么"。

**第二层 —— 进度条。** 用已耗时算出来的估算值驱动，条子有**明确上限**，不突破。

##### 预估值怎么算（给实现的输入，不是最终定稿）

```text
基数 = 15 秒 × (audio_duration / 120) × batch_size
        # 15 秒来自 README 实测：预热后 2 分钟的歌约 15 秒
若本次会话还没成功出过歌：基数 × 2
        # 覆盖服务刚启动时的模型加载（实测第一首 30.7 秒，planner 初始化 138 秒）
预估值 = max(8 秒, 基数)
```

##### 阶段与进度映射

| 已耗时占预估 | 主文案（大字） | 副文案 | 条子 |
|---|---|---|---|
| 0 – 15% | 正在把你的歌词交给模型 | 已经等了 {n} 秒 | 0 – 15%，平滑推进 |
| 15% – 40% | 正在理解歌词，安排段落 | 估计还要 {x} 秒左右 | 15 – 40% |
| 40% – 75% | 正在编曲 | 估计还要 {x} 秒左右 | 40 – 75% |
| 75% – 100% | 正在演唱 | 估计还要 {x} 秒左右 | 75 – 90% |
| 超过预估仍未完成 | 还在唱，比平时久一些 | 已经等了 {n} 秒，还在等 | **换成流动条纹**，不再显示剩余时间 |
| 完成 | 好了，出歌用了 {n} 秒 | — | 一次性走满 100% |

其中 `{x} = max(3, round(预估值 - 已耗时))`。

##### 三条硬底线（写进验收）

1. **不出现假百分比。** 界面文案里禁止出现「已完成 47%」「47%」「剩余 00:12」这一类把估算当真实进度的表述。数字只允许以「已经等了 N 秒」和「估计还要 X 秒左右」两种形式出现，后者必须带「估计」。条子本身是纯视觉，不标刻度数字。
2. **不卡在"马上就好"。** 条子封顶 90%。一旦超过预估值而任务还没完成，**形态从"进度条"切换为"流动条纹"**，并明说"比平时久一些"。这样用户永远不会盯着一个停在 90% 不动的条子猜"是不是死了"。
3. **固定免责脚注。** 每次生成都显示，不允许随状态消失：

   > 这条进度是按以往耗时估算的，不是模型的真实进度。出歌期间请不要关掉这个窗口。

##### 屏幕 3 线框（正常等待）

```text

│                                                                      │
│                               正在编曲                               │
│                                                                      │
│        ████████████████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░        │
│                                                                      │
│                  已经等了 12 秒 · 估计还要 8 秒左右                  │
│                                                                      │
│           这条进度是按以往耗时估算的，不是模型的真实进度。           │

│                            │    取消    │                            │

└──────────────────────────────────────────────────────────────────────┘
```

##### 屏幕 3-b 线框（比预估久很多）

```text
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│                         还在唱，比平时久一些                         │
│                                                                      │
│         ──────────────▶  流动条纹，无百分比  ──────────────          │
│                                                                      │

│                      或者显卡正被别的程序占用。                      │
│                                                                      │
│               ┌──────────────────────────────────────┐               │
│               │  [ 看看环境有没有问题 ]    [ 取消 ]  │               │
│               └──────────────────────────────────────┘               │
└──────────────────────────────────────────────────────────────────────┘
```

##### 前端怎么让条子"活着"（实现提示）

服务端事件 5 秒一次，太稀。做法：后端在收到 `on_progress(elapsed, status)` 时把 `elapsed` 原样透出；前端用一个约 200ms 的本地定时器，按「已耗时 / 预估值」补间推进条子。这样既不依赖服务端频率，也仍然是"估算"——所以免责脚注不能省。

##### 超时与失败

| 情况 | 对应 CLI | 界面表现 |
|---|---|---|
| 歌词有 error 且未确认 | 返回码 `3` | 回到表单，焦点对准问题项（P0-4 已拦，正常不该走到这） |
| 提交失败（连不上/HTTP 错） | 返回码 `4` | 走 §4.6 环境异常页 |
| 生成失败（`status=2`） | 返回码 `5` | 「这次没生成出来」+ 服务端返回的错误详情（放在可展开区）+ 「再来一次」 |
| 等待超时（默认 1800 秒） | 异常 | 「等太久了，已停止等待」+ 提示模型可能没加载完 + 指向环境自检 |

```text
│                                                                      │
│   你电脑上负责「真正写歌」的那个程序没有在运行，所以现在点也没用。   │
│   它是另外的一个软件，需要先单独打开它。                             │
│                                                                      │
│   怎么打开：                                                         │
│     1. 找到你解压 ACE-Step 的那个文件夹（名字里带 ACE-Step-1.5）     │
│     2. 双击里面的  start_api_server.bat                              │
│     3. 等它出现一行带 8001 的字，再回来点「我再试一次」              │
```

- 「查看完整环境自检」直接渲染 `doctor.run_doctor()` 的 `DoctorReport`：

```text
 │                        │ ◀─ status=0 ────────────────── │
 │                        │ ◀─ status=1 + file_url ─────── │
 │                        ├─ 下载文件 → songs/             │
 │                        ├─ write_sidecar()               │
 ◀── 播放器 + 下载按钮    │                                │
 │                        │                                │
```

注意：**歌词体检完全不发网络请求**，纯本地计算，所以能做到毫秒级实时反馈。这是本设计能成立的关键。

## 5. 待确认问题

需要作者拍板的点，按影响面排序。

**Q1｜一键启动脚本的「一键」边界到哪？**
脚本要不要在检测到 Python 缺失时自动下载安装？我的建议是**不装，只给指引**（一个能让用户直接点的下载链接 + 「装的时候记得勾选 Add to PATH」）。理由：自动装解释器是重操作，容易装坏、容易被杀软拦，也会让"clone 下来就能跑"的承诺变成"要先跑个安装器"。
→ 请确认：**只给指引** / 自动装。

**Q2｜浏览器怎么打开？**
两种：① 脚本自动调 `webbrowser.open()`；② 只在终端打印地址让用户自己点。建议 ①（普通人不会手打 `127.0.0.1:8765`），同时保留 ②作为兜底。
→ 请确认：是否接受启动脚本自动拉起浏览器。

**Q3｜Web 端口选哪个？被占用怎么办？**
建议固定 `8765`，被占用时**自动顺延**到下一个可用端口，并在启动窗口里打印实际用的是哪个。原因是固定的地址方便写进公众号文章（"地址永远是 127.0.0.1:8765"）。
→ 请确认：端口号偏好，以及「顺延」还是「报错让用户改」。

**Q4｜界面上的免责脚注会不会显得像在推责任？**
§4.4 的第三条底线要求每次生成都显示「这条进度是估算的，不是真实进度」。这会占掉界面一行。我认为**必须留**——用户明确要了进度条，而 API 给不出来，不解释就是在骗人。但措辞可以商量（比如改成「进度是估的，慢一点很正常」这种更轻的说法）。
→ 请确认：是否保留固定脚注，以及措辞倾向（严谨 / 轻松）。

**Q5｜Web 层允不允许复用 `cli.py` 里的函数？**
`default_out_name()`、`write_sidecar()`、`human_duration()` 都在 `cli.py` 里，Web 层直接复用最省事，但会让 `cli.py` 承担"公共工具"的角色。另一种做法是把这些搬到新模块，`cli.py` 改为 import——**但这会动到现有文件，有碰坏 57 个测试的风险**。
→ 请确认：优先「Web 层 import cli.py 的现有函数」（改动小、风险低），还是「抽公共模块」（结构更干净、有回归风险）。

**Q6｜界面上要不要显示等价的命令行？**
`write_sidecar()` 已经在写 `reproduce` 字段。给普通人看命令行文本可能反而困惑，但作者可能需要（写文章、答疑、排查）。
→ 我的建议：放进「这首歌的参数」折叠区，默认不展开。请确认是否可接受。

**Q7｜输出文件名：沿用时间戳，还是让用户填？**
现在默认 `song-MMDD-HHMM`。让用户填「这是给谁做的」显然更贴心，但 README 里明确记了"中文 caption 截出来的文件名在 Windows 上容易踩编码和非法字符的坑"。
→ 请确认：需要在界面提供自定义文件名吗？如果需要，是否接受加一层非法字符过滤 + 回退到时间戳？

**Q8｜歌词有 error 时，界面的门禁多严？**
CLI 的行为是：有 error 直接中止（返回 3），要加 `--force` 才继续；有 warn 要加 `--yes`。
→ 我按「error 时按钮变成需二次确认 + 显式『我知道，还是生成』」来设计的，等价于 `--force`。请确认这个强度是否合适，还是干脆硬拦（不给 `--force` 出口）。

**Q9｜Web 服务要不要加最小鉴权？**
当前设计只绑 `127.0.0.1`。理论上同一台机器上的其他用户、或浏览器里装了的扩展，都能访问这个端口并触发耗显存的生成任务。
→ 我的判断是**本版不加鉴权**（跟"本地工具"的定位一致，加了反而麻烦）。请确认这个取舍，以及是否需要给生成接口加一个"同时只允许一个任务"的并发锁（防止误连点把显存打爆）。

**Q10｜「完整项目结构」要走到哪一步？**
§3.4 只加了代码层面的东西。要不要再补 `CHANGELOG.md`、`CONTRIBUTING.md`、`.github/workflows/`（跑测试）、`screenshots/`（界面对比图）？
→ 我的建议：`CHANGELOG.md` 和 `screenshots/` 值得加（公众号文章要用图），CI workflow 在零依赖前提下几乎没成本也值得加，`CONTRIBUTING.md` 对读者价值低、可省。请确认。
